# New Asset Creation Contract

Start with an asset concept, not another gallery design. Recover current Git main, FINAL-GDD.md, the pinned AICP/UGDS references in CODEX-ONE-SHOT.md, ASSET-CONTRACT.md and current technical status in RELEASE.md. Each cloud task is isolated; use its existing checkout, not a new worktree unless requested.

1. Resolve this asset's material identity, perspective, native dimensions, states/animation, timing, constraints, rights/provenance, intended integration and visibility. Routine decoration needs proportionate discussion. Preserve actual editable source; a concept still is not a playable character.
2. Obtain explicit asset-specific Design/Asset Freeze and publication authorization, identifying actual source revision and behavior. Library v1 authorization does **not** authorize future asset publication. Do not synthesize approval or infer rights from a public file.
3. Package under `assets/<plural-type>/<stable-id>/` with `asset.json`, README, runnable source or immutable references, metadata/anchors/timing, applicable LICENSE/NOTICE, hashes, limitations and verification evidence. Retain upstream bytes and exact commit/source paths. Use existing schema fields plus the compatible extensions documented in ASSET-CONTRACT.md.
4. Permanent derivatives need their own stable ID, `parent: {id, revision, summary}` with the exact parent library commit, independent source/output hashes, inherited/adapted licenses and new acceptance scope. Never overwrite another game's pinned assets.
5. Declare capabilities truthfully. Supported adapters are metadata, lawful raster image, and the four vetted PixelFX modules. A new normal image or metadata entry needs only package data and `npm run catalog && npm run build`: no category/layout/page edits. An unsupported executable format needs a bounded, reviewed adapter extension under that asset's authorization; catalog strings never become dynamic script imports. New type names are derived automatically. Localized type/metadata labels can be added to the central dictionary/data without changing layout.
6. Validate the source and actual playback/export, target input, rights and fallback states. Use `npm run validate`, `npm run build`, `npm test`, and relevant browser checks. `npm run assets` regenerates only the four v1 PixelFX exports; do not use it to invent new assets. Keep independent creative/integration/rights/preview/export statuses. An isolated demo is not cross-project verification.
7. Commit/push recoverable source and evidence. Merge/publish only within this asset's explicit authorization and repository rules; the existing Pages workflow deploys main to the same approved gallery. Do not push an unauthorized future asset to main. Verify the live commit and representative interaction before reporting publication.

Use immutable library commit + asset ID + exact entry point in a consuming game's FINAL GDD, with permitted adaptations and rights conditions. Import the artifact; do not reconstruct its creative identity from a screenshot. No automatic updates to consumers.
